# MeshCore OBD-II Vehicle Telemetry Node ## 1. Project Goal Build a small, low-power vehicle telemetry device that plugs into a vehicle's OBD-II port, reads standard OBD-II/CAN information, maintains an accurate estimate of distance traveled, and reports vehicle telemetry over MeshCore. ### Initial target vehicles The device should ultimately work with: * 2006 Toyota RAV4 * ~2010 Chevrolet 
Silverado * 2025 Ford Maverick The first development vehicle should be the **2006 RAV4**. ### Primary objective The first useful application is vehicle mileage tracking. The device should maintain: * Vehicle identity * Accumulated distance measured from vehicle speed * Current trip distance * Current vehicle speed * Ignition/vehicle-active state * Device battery voltage * Last telemetry 
transmission The device should **not initially depend on reading the vehicle's actual odometer value**. Instead, it will calculate distance traveled by integrating vehicle speed over time. Future features: * GPS location and GPS-derived distance * OBD-II trouble-code reporting * Additional engine/vehicle telemetry * More sophisticated vehicle-specific CAN decoding * Possibly a central MeshCore 
telemetry collector --- # 2. Hardware Architecture ## Primary prototype hardware ### MCU / radio **Heltec WiFi LoRa 32 V4** * ESP32-S3 * SX1262 LoRa radio * Li-ion battery interface/charging * OLED * GNSS connector for future expansion * MeshCore-compatible The V4 has a dedicated 1.25 mm GNSS connector and improved battery management, which makes it particularly useful for the planned future 
GPS version. Heltec specifies a 3.3–4.4 V lithium battery input. ### CAN transceiver **SN65HVD230** The ESP32-S3 contains the TWAI/CAN controller but does not contain the physical CAN transceiver. The SN65HVD230 provides that physical-layer interface. Espressif specifically lists the SN65HVD23x family as suitable for this application. ### Vehicle interface Standard OBD-II male plug: * Pin 4 — 
chassis ground * Pin 5 — signal ground * Pin 6 — CAN High * Pin 14 — CAN Low * Pin 16 — unswitched vehicle battery +12 V For the initial prototype, only CANH, CANL, and ground need to be connected. --- # 3. Recommended Heltec V4 Pin Assignment Use the following pins for the initial design. | Function | Heltec V4 GPIO | SN65HVD230 | | ----------- | -------------: | ----------------- | | CAN TX | 
GPIO3 | TXD | | CAN RX | GPIO4 | RXD | | Ground | GND | GND | | Logic power | 3.3 V | VCC | | CAN High | — | CANH → OBD pin 6 | | CAN Low | — | CANL → OBD pin 14 | ### Why GPIO3/GPIO4? They are exposed on the V4 and are not part of the Heltec's LoRa SPI bus. The V4's LoRa interface occupies GPIO8–14, while GPIO1 is associated with battery measurement and GPIO2 is involved in the LoRa power/RF 
circuitry. GPIO3 and GPIO4 are therefore preferable for a general-purpose peripheral such as CAN. The ESP32-S3 GPIO matrix allows the TWAI TX/RX signals to be routed to these GPIOs. ### Reserve these pins for future functionality Keep these available: | GPIO | Future use | | --------: | -------------------------------------------------- | | GPIO38 | GNSS TX | | GPIO39 | GNSS RX | | GPIO40 | 
GNSS wake | | GPIO41 | GNSS PPS | | GPIO42 | GNSS reset | | GPIO1 | Heltec battery measurement | | GPIO8–14 | SX1262 | | GPIO17/18 | OLED | | GPIO10 | User button / board function depending on revision | The V4's built-in GNSS interface uses GPIO38–42, so reserving those now makes adding GPS later straightforward. --- # 4. CAN Wiring ## SN65HVD230 Prototype wiring: ```text
                 HELTEC V4
              ┌──────────────┐ │ │
        3.3V ─┤──────────────┼──── VCC
         GND ─┤──────────────┼──── GND
       GPIO3 ─┤──────────────┼──── TXD GPIO4 ◄┤──────────────┼──── RXD
              │ │ └──────────────┘
                       │ │
                ┌──────┴──────┐ │ SN65HVD230 │ │ │ │ CANH ───────┼──── OBD pin 6 │ CANL ───────┼──── OBD pin 14 └─────────────┘ ``` Connect the OBD ground to Heltec/transceiver ground. Use either OBD pin 4 or pin 5 as the ground reference; connecting both is reasonable for the prototype. ## CAN termination **Do not add a 120 Ω 
termination resistor.** The device is being attached to an existing automotive CAN bus rather than creating a new standalone CAN bus. Adding termination at the device would alter the vehicle's bus impedance. --- # 5. Vehicle Power ## Initial development Do NOT initially power the Heltec from the OBD port. Power the Heltec independently using: * USB-C, or * its Li-ion battery Connect only: * GND 
* CANH * CANL This makes the first CAN tests electrically simple and avoids introducing automotive power-supply problems. ## Production device Eventually the OBD connector's pin 16 (+12 V) can provide vehicle power. However: **Do not connect OBD pin 16 directly to the Heltec battery input.** The Heltec battery connector expects a single-cell lithium battery voltage, not automotive 12 V. The 
final design should instead have an automotive-rated power stage, approximately: ```text OBD pin 16
    │ ▼ automotive transient protection │ ▼ buck regulator │ ├──► ESP32 / CAN electronics │ └──► battery charging system ``` The exact power architecture will be designed after the CAN/software prototype is working. Important future considerations: * load dump/transient protection * reverse polarity protection * vehicle battery undervoltage * quiescent current * ignition detection 
* sleep current * avoiding vehicle battery drain when parked --- # 6. Software Architecture The software should be separated into independent layers. ```text ┌──────────────────────────────────────────────┐ │ MeshCore telemetry │ ├──────────────────────────────────────────────┤ │ Vehicle data 
model │ ├──────────────────────────────────────────────┤ │ Mileage / trip calculation │ ├──────────────────────────────────────────────┤ │ OBD-II protocol │ ├──────────────────────────────────────────────┤ │ CAN / TWAI │ 
├──────────────────────────────────────────────┤ │ SN65HVD230 physical layer │ └──────────────────────────────────────────────┘ ``` This separation is important because the same OBD code should eventually be usable regardless of whether the output is MeshCore, USB serial, Wi-Fi, or something else. 
--- # 7. Development Phase 1 — CAN Sniffer The first firmware should do nothing vehicle-specific. Configure the ESP32-S3 TWAI controller for: * 500 kbit/s * standard 11-bit CAN identifiers initially * listen-only mode * no CAN transmission ESP32-S3 TWAI explicitly supports listen-only mode, in which the controller receives traffic without transmitting or acknowledging frames. This is ideal for 
the first vehicle test. Serial output should resemble: ```text CAN 0x123 DLC=8 12 34 56 78 9A BC DE F0 CAN 0x456 DLC=8 00 00 01 42 80 00 00 00 CAN 0x7DF DLC=8 02 01 0D 00 00 00 00 00 ``` The initial goal is simply: > Plug into the RAV4 and reliably observe CAN traffic without transmitting anything. ### Tests 1. Verify transceiver supply voltage. 2. Verify CANH/CANL wiring. 3. Connect device to 
RAV4. 4. Observe traffic with ignition off. 5. Turn ignition on. 6. Observe traffic. 7. Start engine. 8. Observe traffic. 9. Record CAN traffic for several minutes. 10. Confirm the device does not generate CAN errors. Save captures for later analysis. --- # 8. Development Phase 2 — Standard OBD-II Requests Once passive reception works, enable normal TWAI transmission. Start with standard OBD-II 
requests rather than proprietary CAN decoding. The primary request should be: ```text Mode 01 PID 0D Vehicle speed ``` Typical request: ```text CAN ID: 0x7DF 02 01 0D 00 00 00 00 00 ``` Typical response: ```text 41 0D XX ``` where XX represents vehicle speed in km/h. The exact response IDs and protocol behavior should be confirmed on each vehicle. ### Other useful initial PIDs Eventually test: 
* 01 0C — engine RPM * 01 0D — vehicle speed * 01 05 — coolant temperature * 01 04 — calculated engine load * 01 0F — intake air temperature * 01 2F — fuel level * VIN request * supported-PID queries The device should maintain a vehicle capability table rather than assuming every vehicle supports every PID. --- # 9. Vehicle Profiles The software should have a generic OBD layer plus optional 
vehicle profiles. Example: ```text VehicleProfile
    name protocol CAN bitrate request ID response ID supported PIDs polling interval quirks ``` Initial profiles: ```text Toyota RAV4 2006 Chevrolet Silverado ~2010 Ford Maverick 2025 Generic OBD-II ``` The generic profile should be attempted first. If a vehicle requires special handling, that behavior should be isolated to its profile rather than scattered throughout the main program. --- # 
10. Development Phase 3 — Mileage Calculation Do not initially attempt to read the vehicle's actual odometer. Instead calculate distance from vehicle speed. Conceptually: ```text distance += speed × elapsed_time ``` Example: ```text speed = 60 km/h elapsed = 1 second distance += 60 / 3600 km ``` Convert internally to a suitable fixed-point representation. Recommended internal unit: 
**millimeters or meters** rather than floating-point miles. For example: ```text uint64_t total_distance_mm uint64_t trip_distance_mm ``` This avoids accumulating floating-point error over long periods. Display/telemetry can convert to miles. --- # 11. Trip Detection A trip begins when: ```text vehicle becomes active AND vehicle speed / engine state indicates operation ``` A trip ends after a 
configurable period of inactivity. For example: ```text Ignition active
      │ ▼ Start trip │ ▼ Poll vehicle │ ├── speed > 0 ──► accumulate distance │ ▼ Ignition/inactivity │ ▼ End trip ``` The exact sleep/ignition detection mechanism should be determined experimentally. --- # 12. Persistent Mileage Mileage must survive: * ESP32 reboot * battery replacement * MeshCore reboot * temporary CAN failures * firmware restart Store periodically in 
nonvolatile storage. Example: ```text vehicle_total_distance trip_distance vehicle_id last_trip_timestamp ``` Do not write flash on every speed sample. Instead: * accumulate in RAM * periodically checkpoint * checkpoint when a trip ends * checkpoint before intentional shutdown For example, a checkpoint every 0.1–1.0 mile or every several minutes, whichever comes first. The exact interval can be 
tuned after measuring flash wear and power-loss behavior. --- # 13. MeshCore Integration Once CAN and mileage are reliable independently, integrate MeshCore. MeshCore already has a telemetry framework and sensor infrastructure, including battery-voltage telemetry and sensor querying. It also supports custom variables and custom/binary packets. The preferred design is to treat the vehicle as a 
**MeshCore sensor node**. Potential telemetry: ```text vehicle_id = RAV4 distance = 184321.72 mi trip = 12.43 mi speed = 42 mph engine = running battery = 4.02 V ``` The actual wire representation should be compact binary rather than repeatedly transmitting verbose text. --- # 14. Telemetry Frequency Do not transmit vehicle speed every second over MeshCore. Instead: ### Locally Sample vehicle 
speed approximately once per second. ### MeshCore Transmit approximately: * on trip start * periodically during a trip * on trip end * when requested * when significant events occur For example: ```text Trip start
     ↓ telemetry Every 1–5 minutes ↓ telemetry Trip end ↓ telemetry ``` The exact interval should depend on MeshCore network traffic and battery consumption. A telemetry request mechanism can also be used so the network can query the current vehicle state when needed. MeshCore's current protocol includes telemetry requests/responses. --- # 15. Proposed Vehicle Telemetry Data Initial logical 
data model: ```text VehicleTelemetry vehicle_id vehicle_name total_distance trip_distance speed engine_rpm vehicle_active engine_running device_battery_voltage last_can_activity last_obd_response obd_connected ``` Not every field needs to be transmitted every time. --- # 16. Vehicle Identification The device should eventually retrieve the VIN using standard OBD functionality. This allows: 
```text VIN → vehicle identity ``` instead of manually configuring: ```text THIS DEVICE = RAV4 ``` The VIN can be stored locally after the first successful read. Possible workflow: ```text New vehicle
    ↓ Query VIN ↓ Store VIN ↓ Match vehicle profile ↓ Begin normal telemetry ``` For privacy, VIN should not necessarily be transmitted over MeshCore by default. A locally configured short identifier such as: ```text RAV4 SILVERADO MAVERICK ``` is preferable for normal telemetry. --- # 17. Future GPS Expansion The Heltec V4 was deliberately selected partly because it has a dedicated GNSS 
interface. Heltec exposes GNSS-related pins including TX, RX, wake, PPS, and reset. Future architecture: ```text
                    ┌──────────────┐ │ GNSS │ └──────┬───────┘
                           │ ▼ CAN ──► ESP32-S3 ◄──── GNSS
          │ ├── mileage ├── speed ├── location ├── trip │ └── MeshCore ``` GPS can provide: * latitude * longitude * speed * heading * trip distance * time synchronization GPS-derived speed/distance should initially be treated as **additional data**, not a replacement for OBD speed. Eventually we can compare: ```text OBD distance vs. GPS distance ``` to identify discrepancies. 
MeshCore already has GPS-related support, including location handling and GPS time synchronization. --- # 18. Future Trouble-Code Reporting Add read-only diagnostic trouble-code support. Initial goal: ```text Request Mode 03
        ↓ Read stored DTCs ↓ Decode ↓ Transmit over MeshCore ``` Example conceptual output: ```text Maverick DTC: P0301 P0420 ``` The device should **not initially implement clearing codes**. Reading diagnostic information is substantially safer than automatically sending a "clear DTCs" command. Later, additional diagnostic modes can be investigated: * Mode 03 — stored DTCs * Mode 07 — 
pending DTCs * Mode 0A — permanent DTCs Some newer vehicles may use additional gateway/UDS behavior, so the 2025 Maverick should be treated as a separate testing phase rather than assuming the 2006 RAV4 behavior will carry over. --- # 19. Low-Power Architecture The final device should spend most of its parked life asleep. Desired behavior: ```text
                  Vehicle parked
                       │ ▼
                 Deep sleep
                       │ │ vehicle activity ▼
                 Wake ESP32
                       │ ▼
                  Initialize CAN
                       │ ▼
                  OBD communication
                       │ ▼
                 Vehicle running
                       │
              ┌────────┴─────────┐ │ │
          CAN polling MeshCore
              │ │ └────────┬─────────┘
                       │ ▼
                 Vehicle stops
                       │ ▼
               Save mileage
                       │ ▼
                  Deep sleep ``` The wake strategy should be determined during hardware testing. Possible methods: 1. ignition detection 2. CAN bus activity detection 3. periodic wake 4. combination of the above The final design should prioritize extremely low parked current because the OBD port is normally permanently powered. --- # 20. Testing Plan ## Stage A — Bench electronics Before 
connecting to a vehicle: * Verify Heltec 3.3 V rail. * Verify SN65HVD230 supply. * Verify TX/RX logic levels. * Confirm GPIO3/GPIO4 operation. * Confirm CAN transceiver output. * Confirm no accidental LoRa pin conflicts. Test ESP32 TWAI in internal/no-acknowledgement or loopback mode first. --- ## Stage B — Passive RAV4 CAN monitoring Configure: ```text 500 kbit/s listen-only ``` Connect: 
```text CANH → OBD 6 CANL → OBD 14 GND → OBD 4/5 ``` Do not transmit. Test: 1. vehicle off 2. ignition on 3. engine running 4. accessories operating 5. short drive Save CAN captures. --- ## Stage C — OBD request testing Enable transmission. Test one PID at a time: 1. supported PID query 2. vehicle speed 3. RPM 4. coolant temperature 5. engine load 6. fuel level 7. VIN Confirm responses are 
correct before proceeding. --- ## Stage D — Mileage Test against a known route. For example: ```text Start: total = X trip = 0 Drive known route. End: trip = calculated distance total = X + trip ``` Compare against: * vehicle trip computer * GPS * mapping distance The objective isn't necessarily perfect agreement to the tenth of a mile; we want stable, repeatable accumulated mileage. --- # 21. 
Cross-Vehicle Testing After the RAV4 works: ### Silverado Test: * CAN bitrate * OBD request behavior * speed PID * RPM * VIN * DTCs Record any differences. ### 2025 Maverick Treat this as the most complicated test vehicle. Test: * standard OBD connection * CAN/OBD protocol * gateway behavior * supported PIDs * VIN * DTC behavior Do not assume that proprietary CAN traffic visible on the bus can 
be safely queried or interpreted merely because standard OBD works. --- # 22. Fault Handling The firmware should tolerate: * no CAN connection * CAN bus errors * unsupported PIDs * malformed responses * temporary OBD communication failure * vehicle shutdown * MeshCore unavailable * MeshCore transmission failure * ESP32 reboot Mileage calculation should continue to work independently of 
MeshCore. For example: ```text CAN ──────► Mileage engine ──────► persistent storage
                 │ └───────────────► MeshCore ``` MeshCore must never be a dependency for maintaining mileage. --- # 23. Suggested Software Modules Organize the project approximately as: ```text /src

Important Design Principles 1. **Do not depend on proprietary CAN decoding for basic mileage.** 2. **Use standard OBD-II wherever possible.** 3. **Calculate distance locally.** 4. **Persist mileage independently of MeshCore.** 5. **Do not transmit raw CAN traffic 
over MeshCore.** 6. **Keep vehicle-specific behavior in profiles.** 7. **Keep DTC reading separate from DTC clearing.** 8. **Design parked power consumption as a first-class requirement.** 9. **Reserve the V4 GNSS pins now.** 10. **Keep the CAN hardware electrically independent from the LoRa hardware.** 11. **Start with listen-only CAN monitoring before transmitting anything to a vehicle.** 12. 
**Test the 2006 RAV4 first and use it as the reference implementation.** --- # 27. Immediate Next Steps While waiting for the hardware: 1. Set up the ESP32-S3 development environment. 2.
